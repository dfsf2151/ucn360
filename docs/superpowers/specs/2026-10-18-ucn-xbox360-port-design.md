# نقل Ultimate Custom Night (نسخة HTML5) إلى Xbox 360 — مواصفة تصميم

- **التاريخ:** 2026-10-18
- **الحالة:** بانتظار مراجعة المستخدم (لا تنفيذ قبل الموافقة)
- **المشروع:** `/home/mohamd/Projects/UCN_MVP_Xbox360`
- **القرار المرجعي:** الخيار 1 — محرك C++ يشغّل بيانات اللعبة الأصلية (ccj + الأصول الحقيقية)، والمخرج النهائي **XEX** يُشغَّل من Aurora.

---

## 1. الهدف

العب UCN نفسها (لا لعبة مُعاد بناؤها) على Xbox 360 معدَّل، بتشغيل `default.xex` واحد من Aurora. المحرك الجديد يقرأ **نفس ملفات اللعبة الأصلية** ويتصرف بنفس منطق `Runtime.js`:

- نفس بيانات الأحداث: `Application.ccj` (16 إطارًا، 2520 مجموعة أحداث).
- نفس الصور: 388 ملف PNG (241 أطلس `M####` + 147 مباشر).
- نفس الأصوات: 608 ملف ogg/mp3.
- نفس المنطق: 53 Action و35 شرطًا مستخدمة فعلًا + أشجار التعبيرات، تُفكَّك وتُفسَّر بمنطق `Runtime.js` الحقيقي.

**غير مطلوب:** إعادة إنتاج خصائص لم تستخدمها اللعبة (مجسمات 3D، فيزياء، شيدرز معقدة...إلخ).

## 2. معايير النجاح (قابلة للقياس)

1. `default.xex` يُقلع من Aurora على الجهاز (FreeMyXe) ويصل لواجهة اللعبة.
2. القوائم والإطارات والألعاب المصغّرة تعمل: التنقل، إدخال الأسماء/الشخصيات بالنقر، تشغيل أي إطار من الإطارات الستة بلا انهيار.
3. مطابقة السلوك لمرجع المتصفح (web_probe) عند نفس الإدخال ونفس عدد الـticks: مواضع الكائنات/الحركات/الحالات مطابقة.
4. الصوت يعمل (مؤثرات + موسيقى) والحفظ يبقى بعد إعادة التشغيل.
5. أداء مستهدف: 60 إطارًا/ثانية بلا تقطيع في المشاهد المزدحمة.

## 3. حقائق مُثبتة (ملخّص أدلة الجلسات السابقة)

- استُرجعت **999/999** ملفًا من الأرشيف المجزّأ (CRC سليم) → `assets_raw/out/` (314MB).
- نسخة اللعبة الحيّة تعمل في `web_probe/` (خادم 8765 + Chrome headless عبر CDP، مع أدوات لقطة/مفاتيح/eval).
- تم تفريغ كل بيانات محرك اللعبة:
  - `assets_raw/dump/defs_merged.json` — 638 تعريف كائن (442 بأنيميشن، 631 حركة، 145 عدّادًا).
  - `assets_raw/dump/frames.json` — تفريغ الإطارات الـ16.
  - `assets_raw/dump/required_files.json` — ملفات كل إطار.
- نموذج الصور مُفكّك: `wb=Un[handle]` (0 → ملف مباشر `####.png`، وإلا أطلس `M####.png` مقصوص عند `rd,sd`)، بنك 2158 مقبضًا.
- أحداث ctfak تُعطي البنية (أعضاء المجموعات) لكن قيم التعبيرات مشوّهة (خطأ int32/double)، لذا سنفكّك التعبيرات بأنفسنا وفق `N.load`/`G.create` في `Runtime.js`.
- `Runtime.js` يعمل بحلقة `requestAnimationFrame` (مع `setTimeout` احتياطيًا)، والمدخلات عبر `canvas.Uc.Jc[keyCode]`، والصوت عبر `Audio` أو WebAudio (فك كامل للملف ثم تشغيل)، والحفظ عبر `localStorage`.
- **Xenia Edge (Linux AppImage) موجود محليًا** → اختبار دخان سريع للـXEX قبل تسليمه للمستخدم.

## 4. المنصة المستهدفة: **xsdk**

مكتبة/إطار عائم (`github.com/xenosworks/xsdk`، رخصة MIT) تنتج **XEX2 حقيقية** تعمل على النواة الأصلية (RGH/FreeMyXe) عبر `tools/elf2xex.py`، وتغطي كل ما نحتاجه:

| القدرة | الواجهة |
|---|---|
| رسم GPU مباشر (Xenos): رؤوس/فهرسات، مزج، مقص، منافذ عرض | `include/xsdk/gpu.h` |
| أهداف eDRAM + resolve إلى الذاكرة/الزمن الأمامي | `gpu.h` (`set_target`, `resolve`, `present`) |
| خطوط أنابيب 2D: نسيج + لون لكل رأس، DXT1/3/5، mips، sampler | `texture.h` |
| شيدرز GLSL تُصرَّف إلى microcode (XSC) وقت البناء أو التشغيل | `shader.h`, `xsc.h`, `tools/gen_*` |
| عرض 720p متزامن مع vblank + تكامل مع Guide | `present.h`, `display.h` |
| ملفات `game:\` (مجلد الإقلاع، قابل للكتابة) عبر newlib | `src/file.c` |
| يد تحكم | `XamInputGetState` في `kernel.h` |
| صوت: عميل render driver بمعدل 48kHz، إطارات 6 قنوات float | `XAudioRegisterRenderDriverClient` |
| خيوط + مزامنة (استغلال 3 أنوية/6 خيوط) | `thread.h`, pthreads |

**الأدوات:** سلسلة `powerpc-xsdk-elf` (GCC 15 + newlib) تُبنى بسكربت `tools/toolchain/build.sh` إلى `~/xsdk-gcc`. البناء والنمذجة في `Makefile`/CMake الخاصة بـxsdk، والتغليف بـ`elf2xex.py`.

**الخطة الاحتياطية:** إن ظهرت مشكلة توافق على جهاز المستخدم (FreeMyXe + xsdk)، نعود إلى مسار libxenon (XeLL يحمّل ELF) الذي بنيناه سابقًا — نفس المحرك، خلفية منصة مختلفة فقط.

## 5. المعمارية

> **تحديث معماري (2026-10-18، أثناء التنفيذ):** بعد فحص محرك اللعبة الحيّ (`window.__rt.Uc`) تبيّن أننا لسنا مضطرين لفكّ تنسيق ccj الثنائي داخل الجهاز: محرك اللعبة الحيّ يُظهر:
> - برنامج الأحداث **المُصرَّف** كاملًا (`frame.un` مع 554 مجموعة في إطار Frame 1 وأمثالها)،
> - تعريفات الكائنات (أنيميشن/عدادات/قيم) بصيغة صحيحة،
> - جداول الصور لكل إطار (handle → أطلس/ملف + مستطيل القص + القياسات).
>
> لذلك صار مسار البيانات: **مُصرِّف offline** (`tools/compile_bundle.py`) يبني حزمة بيانات (`bundle.bin`) من تفريغات المحرك الأصلي (المُتحقَّق منها مقابل ctfak JSON) + الأصول، والمحرك على الجهاز **يقرأ الحزمة** فقط — لا فكّ تنسيقات ثنائية معقّدة على الجهاز. يُبقي هذا نفس الدقة (البيانات هي بيانات اللعبة الأصلية) ويقلّل مخاطر الجهاز. ملف `Application.ccj` يبقى مرجعًا للمقارنة وقت التطوير.

```
UCN_MVP_Xbox360/
├─ engine/                  ← محرك قابل للنقل (C++17، بلا اعتماديات منصة)
│  ├─ ccj/                  قراءة الحزمة bundle.bin (بديل ccj على الجهاز)
│  ├─ evm/                  آلة الأحداث: actions/conditions/expressions
│  ├─ game/                 الكائنات، الأنيميشن، الطبقات، الانتقالات، منطق اللعب
│  ├─ assets/               بنوك الصور/الأصوات، مسارات الملفات، cache (LRU)، فك ogg/mp3
│  ├─ audio/                الخلاط: 32 قناة، حلقة، سرعة، مستوى + resample
│  └─ render/               بناء قائمة الرسم (quads + ترتيب + مزج) كنموذج محايد
├─ platform/
│  ├─ host/                 لبناء لينكس: إطار مقاس + تفريغ PNG/مقارنة تلقائية (وضع headless)
│  └─ xenon/                لـxsdk: batcher GPU + XSC shaders + present 720p + إدخال + صوت + ملفات
├─ tools/
│  ├─ dump_oracle.js        تفريغ المحرك الحيّ: برنامج الأحداث + التعريفات + الإطارات + الصور
│  ├─ compile_bundle.py     بناء bundle.bin + bundle.json من التفريغات
│  ├─ asset_pack.py         PNG → DXT (+قياسات) وبناء manifests لكل إطار
│  ├─ gen_shaders.py        GLSL → microcode عبر libxsc.so (يُدمج كـ header)
│  └─ build_xex.sh          بناء xenon + elf2xex + تجهيز dist/
├─ third_party/xsdk/        نسخة مثبتة (commit محدّد) من xsdk
├─ web_probe/               مرجع المتصفح (موجود)
└─ dist/ucn360/             { default.xex, resources/, README.txt }
```

خلفية العرض تُبنى على نموذج واحد: قائمة quads (نسيج + مستطيل + مستطيل مصدر + لون/ألفا + ترتيب). الـhost يرسمها برمجيًا (مقارنة/لقطات)، وxenon يرسمها عبر GPU بدفعة واحدة لكل إطار.

## 6. المحرك — تفاصيل

- **قراءة ccj:** نفس ترتيب `Runtime.js` (`N.load`): مقاطع `ER>>`, `ERes`, `ERev`, `<<ER`... تُتحقق بالمقارنة مع تفريغاتنا الحيّة.
- **آلة الأحداث:** تمثيل المجموعات (Conditions + Actions) وشجرة المجموعات؛ تنفيذ الـ53 Action/35 Condition المستخدمة + التعبيرات (operations, variables, timers, distances, etc.) بمنطق مطابق لـ`G.create`.
- **المنطق الزمني:** حلقة بخطوة ثابتة (نحدد معدلها وطريقة delta من مراقبة `Runtime.js`، مرجح 60Hz) مع فصل الرسم عن المنطق.
- **الكائنات:** تعريفات + instances/layers من الإطار النشط؛ الأنيميشن (frames/directions/speed)؛ العدادات والتنسيقات.
- **الانتقالات بين الإطارات:** تحميل الإطار = `app.Db=i; app.tK()` (نفس الدلالات).
- **النقر والإدخال:** حساب النقاط والتصادم كما تفعله اللعبة (bitmap masks عبر عارض `gd` عند الحاجة فقط).

## 7. الرسوميات

- **الهدف:** هدف eDRAM واحد 1280×720 بلا عمق (رسم 2D فقط) ← يتركب داخل eDRAM (720 من 2048 بلاطة).
- **الرسم:** جمع كل العفاريت في مصفوفة رؤوس واحدة (موقع، إحداثيات نسيج، لون) + فهرسات 16-بت، ثم resolve إلى الزمن الأمامي وعرض بـ`xsdk_present` (3 مخازن، swap كل vblank).
- **الشيدر:** زوج بسيط (textured quad + tint + alpha)، يُصرَّف مسبقًا وقت البناء إلى microcode ويُضمن كـ header (لا تصريف على الجهاز).
- **المزج:** افتراضيًا `SRC_ALPHA / ONE_MINUS_SRC_ALPHA`؛ نضيف الأنماط التي تستخدمها اللعبة فعلًا (additive/subtractive) بعد حصرها من البيانات.
- **إسقاط الإحداثيات:** مطابقة سلوك المتصفح: إطار اللعبة بأبعاده المعلنة يُقاس إلى الشاشة بحفظ النسبة (letterbox)، وتحويل إحداثي الماوس بنفس المعامل.
- **النص/الخطوط:** خطوط الصور المدمجة في بنوك اللعبة تُرسم كأي عَفريت — لا حاجة لخطوط TTF.

## 8. الأصول والذاكرة

**التحويل (offline):**
- PNG → DXT: DXT1 إذا كانت قناة alpha ثنائية (0/255)، وإلا DXT5. (قياس فعلي للاختيار أثناء M3.)
- الأصوات تبقى كما هي (ogg/mp3) وتُفكّ في زمن التشغيل.
- `required_files.json` يُحوَّل إلى manifest لكل إطار (ما يجب تحميله عند دخول الإطار).

**الأرقام المقيسة (DXT5 للكل، حالة قصوى):**
- إجمالي كل الـ388 صورة: **384MB** — كلها لا تجتمع في وقت واحد.
- أقصى متطلب إطار: **~384MB** (الإطارات 13–15)؛ أقلها 33MB (INTRO).
- مع DXT1 حيث تسمح alpha، وفروق التحميل الكسول، المتوقع عمليًا 200–300MB.

**الاستراتيجية:**
1. التخزين على القرص ثابت (USB/HDD) بصيغة مضغوطة DXT.
2. تحميل عند الحاجة بمخزون LRU بميزانية مضبوطة (تُقاس في M3)، أولوية لملفات الإطار التالي.
3. عند الإقلاع: INTRO فقط (33MB) → إقلاع سريع.
4. إن تجاوز إطار حاجة الميزانية: خفض إضافي مقصود (قص أطالس غير مستخدمة/إعادة تحجيم آمنة) — القرار مبني على قياس لا تخمين.

**حجم التوزيع المتوقع:** ≈ xex (بضعة MB) + نسيج DXT (200–300MB) + صوت (157MB) ≈ **400–500MB**، تُنسخ إلى USB FAT32 (أو HDD).

## 9. الصوت

- **الخلاط:** 32 قناة (يطابق `U.Sc`)، لكل قناة: play/stop/loop/volume/rate/position، مع `pause/resume`.
- **الفك:** ogg عبر `stb_vorbis`، mp3 عبر `minimp3` (مكتبتان مجانيتان، C نقي، تُنسخان للمشروع).
  - المؤثرات القصيرة: فك كامل + cache في RAM.
  - المقاطع الطويلة (موسيقى): فك تدفقي في الخيط الصوتي.
- **المخرج:** عميل `XAudioRenderDriverClient` (48kHz؛ إطار 6 قنوات × 256 عيّنة float big-endian — الأمثل: تعبئة ستيريو L/R وترك البقية أصفارًا؛ إعادة معايرة 44.1k→48k بترشيح خطي).
- **الالتزام بالسلوك الأصلي:** تشغيل/إيقاف/تكرار/تغيير مستوى أثناء التشغيل كما تفعل أحداث اللعبة.

## 11. البناء والتوزيع

1. بناء سلسلة `powerpc-xsdk-elf` مرة واحدة → `~/xsdk-gcc` (30–60 دقيقة).
2. استنساخ xsdk في `third_party/xsdk` (commit مثبّت) وبناؤه مرة.
3. `tools/build_xex.sh`: يبني المحرك لـxenon → `elf2xex.py` → ينشئ:
   ```
   dist/ucn360/
   ├─ default.xex
   ├─ resources/        (999 ملفًا: dxt + ogg/mp3 + ccj)
   └─ README.txt        (عربي: انسخ إلى USB FAT32، شغّل من Aurora)
   ```
4. اختبار دخان بـXenia محليًا (إقلاع/رسم/لوق) قبل كل تسليم للمستخدم.
5. تسمية العنوان (title id) ثابتة، ومجلد `resources` بجانب الـxex مباشرة (`game:\` = مجلد الإقلاع).

## 12. التحقق والدقة

- **المرجع:** `web_probe` الحيّ عبر CDP — ندير نفس السيناريو (إدخالات في تِكات محددة) ونسجّل: حالات الكائنات (x/y/animation/frame)، الإطار النشط، أعلام الحالة، ولقطات PNG.
- **المطابقة الآلية:** بناء host يقرأ سيناريو (ticks + إدخال) ويخرج JSON؛ سكربت يفرّق مع المرجع ويعرض أول اختلاف (كائن/خاصية/تِك).
- **الاختبار على الجهاز:** أبرز الاختبار النهائي عند المستخدم؛ لذلك نُسلّم مبكرًا: M0 (xex يستجيب) وM4 (نسخة قابلة للعب) لضبط أي خصوصية جهاز.

## 13. المراحل ومعايير القبول

| المرحلة | المخرج | معيار القبول |
|---|---|---|
| **M0 — منصة** | سلسلة xsdk مبنية + عنوان تجريبي `default.xex` (شعار + نص + لوق `game:\`) | المستخدم يشغّله من Aurora فيراه (اختبار توافق FreeMyXe مبكر) |
| **M1 — هيكل المحرك (host)** | قراءة ccj + أطلس/صور + بناء قائمة رسم: INTRO ثم القائمة الرئيسية | لقطة host مطابقة بصريًا لـINTRO/القائمة في المتصفح |
| **M2 — آلة الأحداث** | تنفيذ actions/conditions/expressions + التنقل الكامل حتى دخول Frame 1 | سيناريو آلي: نفس الحالات في المتصفح والمحرك لـ≥2000 ticks |
| **M3 — الأصول والذاكرة** | asset_pack (DXT) + manifests + LRU + قياس أقصى ذروة | تحميل أي إطار بلا تجاوز الميزانية، وزمن تحميل مقبول |
| **M4 — نسخة xenon قابلة للعب** | GPU batcher + present 720p + إدخال يد + صوت أساسي، XEX كامل | المستخدم يلعب INTRO→قائمة→إطار على الجهاز |
| **M5 — الاكتمال** | صوت كامل (تعدد القنوات/الحلقات) + الحفظ + كل الإطارات الستة والعروض | جميع الإطارات تُلعب وتُنهى بلا انهيار |
| **M6 — الإتقان والتسليم** | أداء 60fps، دقة ملاحظات المستخدم، توثيق التثبيت | قبول المستخدم النهائي: «نفس اللعبة» |

## 15. خارج النطاق

- دعم 1080p داخلي (المخرج 720p والجهاز يكبّره؛ القرار قابل للترقية لاحقًا).
- دعم لوحة مفاتيح USB.
- تحويل الأصوات مسبقًا إلى XMA.
- أي ميزة من اللعبة غير المستخدمة في بيانات UCN الفعلية.
